# 인공지능혁신융합대학사업단 회의비 증빙 자동 검수 — 방향성 (2026-10-28)

> 대상: 동아리 담당자 1명, 위밋 담당자 1명의 학교 메일함. 학생 팀이 보낸 회의비 증빙(회의록 + 영수증)을 받아 검수하고, 보완이 필요하면 회신 초안을 만들어 담당자가 한 번 확인한 뒤 바로 보낸다.
> 이 문서는 정식 개발 전 합의용 정리다. 시험 결과는 [`experiments/aicollege_upstage/`](../../experiments/aicollege_upstage/README.md).

## 1. 한 줄 요약

**지침+양식으로 조건을 한 번 만들어 확정해 두고(기준 설정), 회의록이 메일로 들어올 때마다 Upstage로 파싱·추출하고 코드와 LLM이 조건과 비교해 팀별로 정리한다. 보완이 필요하면 초안 메일까지 만들고, 담당자가 확인 후 [전송]한다.**

## 2. 1차 MVP와 무엇이 같고 다른가

| | 1차 MVP (SW중심대학사업단, Upstage Studio) | 이번 (인공지능혁신융합대학사업단) |
|---|---|---|
| 기준 문서 | 공고문 + 붙임 회의비 양식 | 별첨 1(지원비 지출 참고사항) + 별첨 1-1(동아리 회의비 지출 증빙) |
| RuleAgent | Studio 워크플로 `Parse → Extract_Rules`(10개 항목: 1인당 한도, 장소 규칙, 사진 규칙…) | 같은 역할. 서비스 안에서 **1회 실행 후 담당자가 확정**하는 기준 설정 단계 |
| SubmissionAgent | Studio 워크플로 `Parse → Extract_Meeting`(25개 항목) | 같은 역할. **메일이 올 때마다 상시 실행**되는 제출 처리 단계 |
| 비교·판정 | 코드 우선 병합 + LLM | 같은 원칙: 계산은 코드, 의미 판단만 LLM(Solar) |
| 입력 형식 | PDF 위주 | HWP·PDF·DOCX (Upstage가 셋 다 직접 받음, 시험 완료) |
| 결과 | 검수 보고서 | 팀별 제출 이력 + 항목별 판정 + **회신 초안 → 확인 → 전송** |

## 3. 전체 흐름

```
[기준 설정 — 1회, 지침이 바뀔 때만 다시]
 별첨1+별첨1-1 HWP ─▶ Upstage Parse ─▶ Upstage Extract(조건 항목) ─▶ Solar: 조건 초안
                                                                        │ 코드로 검사 가능한 조건 / LLM 판단 조건 / 사람 확인 조건으로 분류
                                                                        ▼
                                                      rules/<프로그램>.yaml (초안) ─▶ 담당자 검토·확정 (버전 기록)

[제출 처리 — 메일이 올 때마다]
 담당자 메일함(동아리 / 위밋) ─Power Automate─▶ 수집함 ─▶ 접수 기록(프로그램, 팀, 보낸 사람, 접수 일시, 첨부)
                                                             │
                                                             ▼
                        Upstage Parse(OCR: 영수증 이미지 글자) + Upstage Extract(회의록·영수증 필드)
                                                             │
                                                             ▼
                        판정: 코드(날짜·금액·시각·지역·요일·인원·팀 이력) + Solar(장소·주류·내용·식비/다과비)
                                                             │
                                                             ▼
                        적합 / 보완필요 / 부적합 / 확인필요 + 항목별 근거 ─▶ 회신 초안
                                                             │
                                                             ▼
 [담당자 화면] 팀별 목록 → 제출 건 → 항목 확인 → 초안 수정 → [전송] ─Power Automate─▶ 학생에게 담당자 이름으로 회신
```

## 4. 기준 설정 (RuleAgent 역할)

- 입력: `별첨1+1-1_회의비_지침과_양식.hwp` (지침 1쪽 + 회의비 양식 2쪽). 원본 HWP에서 구역 단위로 잘라 만들었고 Upstage 파싱을 확인했다.
- Upstage Parse로 표 구조를 읽고, Extract로 조건 항목(한도·시각·지역·결제수단·제출 기한…)과 양식 칸 목록(팀명·회의명·회의일시·장소·내용·참석자·영수증 첨부란·사용 비용·결제자)을 뽑는다.
- Solar가 지침 문장을 **정해진 조건 유형**(예: `per_person_limit`, `pay_before_time`, `weekday_only`, `region`, `pay_after_meeting(식비)`, `pay_before_meeting(다과비)`, `min_meeting_minutes`, `approval_number_required` …)에 매핑해 파라미터를 채운다. 유형에 안 맞는 문장은 '사람 확인' 조건으로 남긴다.
- 결과를 `rules/<프로그램>.yaml`로 저장하고 **담당자가 확인한 뒤에만 판정에 쓴다**. AI가 만든 조건이 바로 판정에 쓰이지 않게 하려는 것이다. 지침이 바뀌면 다시 돌려 차이만 보여 준다.
- 동아리와 위밋은 기준이 다를 수 있어 파일을 따로 둔다. 위밋 지침 문서는 아직 받지 않았다.

## 5. 회의비 조건 (별첨 1 기준, 확정 전 초안)

| ID | 조건 | 판정 방식 | 비고 |
|---|---|---|---|
| R1 | 영수증 첨부, 금액 > 0 | 코드 (Parse의 그림·OCR 텍스트로 교차 확인) | |
| R2 | 연구비카드 매출전표 (간이영수증·현금 불가) | 코드 + Extract | |
| R3 | 승인번호가 정확히 표기된 영수증 | 코드 | |
| R4 | 회의일 = 영수증 거래일 | 코드 | |
| R5 | 평일 사용 (주말 불가) | 코드 | |
| R6 | 20시 이전 결제, 술집·주류 불가 | 코드(시각) + Solar(가맹점·품목) | |
| R7 | 1인당 20,000원 이내 | 코드 | |
| R8 | 식비: 회의 후 1시간 이내 / 다과비: 회의 전 30분 이내 결제 | Solar(식비·다과비 구분) + 코드(시각) | |
| R9 | 회의 1시간 이상 | 코드 | |
| R10 | 가맹점 광주광역시 북구 (동·서·남·광산구 불가) | 코드 | |
| R11 | 회의 장소 카페·식당 불가 (연구실·회의실·실험실) | Solar | |
| R12 | 회의내용 구체적 | Solar | |
| R13 | 참석자 전원 서명 (자필·전자, 워드 작성 불가) | Extract + 칸 안 그림 확인 | '서명 없음'은 확인필요로 (아래 7) |
| R14 | 사용 비용 = 영수증 합계 | 코드 | |
| R15 | 결제자 소속·이름·서명 | Extract | |
| R16 | **사용 후 1주일 이내 제출** | 코드: 메일 접수 일시 − 거래일 | 접수 기록이 있어 이번엔 판정 가능 |
| R17 | **1회/1일** | 코드: 같은 팀 같은 날짜 이전 제출 조회 | 팀별 이력이 있어 판정 가능 |
| R18 | 수업 시간 내 회의 불가 | 사람 확인 | 참석자 시간표 없음 |
| R19 | 카드 사용 1일 전 예약·반납 | 사람 확인 | 서류 밖 절차 |

최종 판정: 회의비로 인정할 수 없는 조건(예: R4·R5·R6·R7·R8·R10·R11)이 미충족이면 **부적합**, 서류를 고치면 되는 조건이 미충족이면 **보완필요**, 확인필요만 있으면 **확인필요**, 모두 충족이면 **적합**. 등급은 기준 설정 파일에서 담당자가 정한다.

## 6. 팀별 정리 (새로 필요한 것)

- 접수 단위: 메일 1통 = 제출 1건. 보낸 사람·제목·본문·첨부·**접수 일시**를 저장한다.
- 팀 식별: 회의록의 팀명(Extract) + 보낸 사람 주소. 처음 보는 조합은 담당자가 팀을 묶어 준다(별칭 관리).
- 팀별 화면에 제출 이력(접수일, 회의일, 금액, 판정, 회신 여부)을 보여 주고, R16·R17은 이 이력으로 판정한다.
- 같은 메일이 두 번 처리되지 않게 메일 ID로 중복을 막는다. 보완 후 재제출은 같은 팀의 새 제출로 연결한다.

## 7. 상시로 도는 제출 처리에서 신경 쓸 것

| 항목 | 내용 |
|---|---|
| 속도 | Extract 1건 17~36초(시험값). 메일 수신과 처리를 분리해 대기열로 돌리고, 화면은 '처리 중'을 보여 준다 |
| 호출 한도 | Information Extract 동기 1초 1건 → 대기열에서 순서대로, 필요하면 비동기 API |
| 비용 | 파일 해시로 파싱·추출 결과를 캐시해 같은 파일을 다시 보내지 않는다. 재판정은 캐시로 |
| 실패 | Upstage 실패·시간 초과는 재시도 후 '확인필요(처리 실패)'로 표시하고 담당자에게 원본을 보여 준다. 멈추지 않는다 |
| AI 값 검증 | Extract 값은 Parse 원문(OCR 포함)에 실제 있는지 대조한다. 없으면 확인필요. 작고 흐린 서명은 Extract가 '없음'으로 읽은 사례가 있어 '서명 없음'은 바로 미충족으로 두지 않는다 |
| 허위 지적 회피 | 학생 본문에는 미충족만, 확인필요는 담당자 메모로만. 전송은 반드시 담당자가 누른다 |
| 개인정보 | 학생 이름·학번·서명·카드번호가 Upstage로 전송된다. 담당자·사업단 동의 필요, 저장 기간·삭제 정책 정하기 |
| 기록 | 제출마다 사용한 기준 파일 버전, 모델 버전, 판정 근거를 남겨 나중에 설명할 수 있게 |

## 8. 담당자 화면 (빠른 확인용)

1. **받은 제출 목록**: 프로그램(동아리/위밋) 탭, 팀, 접수일, 판정 배지, 회신 상태. 보완필요·부적합이 위로.
2. **제출 상세**: 왼쪽은 원본(쪽 이미지, 영수증 확대), 오른쪽은 항목별 판정. 각 항목에 근거(어느 칸, 어떤 값)와 기준. 담당자가 항목 결과를 바로 바꿀 수 있다(바꾸면 초안이 다시 만들어짐).
3. **회신 초안**: 제목·본문 편집, 받는 사람 확인 → **[전송]** (담당자 이름으로 스레드 회신, Power Automate 흐름 ②). 적합이면 '확인 완료' 처리만.
4. **팀 이력**: 팀별 제출·판정·회신 타임라인.

## 9. 메일 연동 (이미 실증)

- 담당자 계정에서 Power Automate 흐름 ① 수집(첨부 포함 우리 메일함으로 전달), 흐름 ② 발송요청 → 담당자 이름으로 학생 스레드 회신. 브랜치 `spike/mail-graph`의 `docs/devlog/2026-10-23-mail-intake.md`, `docs/guides/power-automate-setup.md`.
- 대상 메일함: **동아리 담당자 1명 + 위밋 담당자 1명**. 메일함으로 프로그램(기준 파일)을 정한다.

## 10. 시험으로 확인된 것 (2026-10-28)

- 같은 가상 회의록 HWP·PDF·DOCX 모두 Upstage Parse 통과, 회의록·영수증 값 15/15. Information Extract 23개 필드 중 21개 세 형식 동일. 판정 결과 세 형식 같음(확인필요: 서류로 못 정하는 조건).
- HWP는 서식 정보가 완전한 파일만 Upstage가 받는다. 시험용 샘플은 실제 양식에 값을 채워 만든다(`tools/aicollege_samples.py`).

## 11. 정해야 할 것

- 위밋 지침 문서와 기준(동아리와 같은지)
- 제출 기한 기준 시각: 메일 접수 일시로 볼지, 회의록 작성일로 볼지
- 등급(부적합/보완필요) 배분과 재제출 처리 방식
- Upstage 전송에 대한 개인정보 동의, 결과 보관 기간
- 운영 환경(서버·대기열·DB)과 담당자 화면 접근 방식(학교 계정 로그인 등)

## 12. 다음 단계 (제안 순서)

1. 위반 케이스 샘플(주말, 20시 이후, 주류, 다과비 시각, 북구 밖, 간이영수증, 서명 누락, 1주일 초과)로 세 형식 시험을 넓힌다.
2. 기준 설정 단계 구현: 합친 HWP → 조건 초안 yaml → 담당자 확정.
3. 제출 처리 파이프라인(접수 기록, 대기열, 캐시, 판정, 초안)을 프레임워크 독립 패키지로, 2차 가이드에 맞춰 LangGraph·FastAPI로 감싼다.
4. 담당자 화면(목록 → 상세 → 초안 → 전송)과 Power Automate 흐름 연결.
