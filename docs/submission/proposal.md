# 기획서 (최종본) — 회의비 증빙 자동 검수 Agent

- 과정: Upstage LLMOps 2차 프로젝트 / 7조
- 팀원: 박종희(백엔드·메일 연동·배포), 김동욱(서비스 디자인·프론트엔드), 강지수(AI 검수 정확도)
- 데모: https://meeting-fee-review-agent.vercel.app
- 작성: 2026-11-04

## 1. 문제와 서비스 개요

### 1-1. 누구의 어떤 문제인가

전남대학교 **인공지능○○○○대학사업단**은 학생 팀 약 100개(동아리 41, 위밋 41, 캡스톤 9, AIM 챌린지 3, 해커톤 5)에 회의비를 지원한다. 학생은 회의를 한 뒤 사업단 양식 회의록(HWP·PDF)에 **영수증 사진을 붙여** 담당자 학교 메일로 보낸다.

담당자 2명(동아리 담당자, 위밋 담당자)은 이 메일을 한 건씩 열어 지침 항목을 눈으로 확인한다.

- 영수증: 연구비카드 매출전표인가, 승인번호가 있는가, 평일·20시 전 결제인가, 광주 북구 가맹점인가, 주류가 없는가
- 금액: 1인당 2만 원 이내인가, 회의록의 사용 비용과 영수증 금액이 같은가
- 시간: 회의 60분 이상, 식비는 회의 후·다과비는 회의 전 정해진 시간 안 결제, 사용일로부터 7일 안 제출
- 회의록: 회의일 = 거래일, 장소가 카페·식당이 아닌가, 내용이 구체적인가, 참석자 전원·결제자 서명

문제가 있으면 학생에게 보완 메일을 직접 쓴다. 한 건에 여러 항목을 대조해야 하고, 영수증 사진은 작거나 돌아가 있고, 같은 팀 이름이 여러 프로그램에 있어 분류도 손이 간다. 제출이 몰리는 주에는 검토가 밀린다.

### 1-2. 서비스 개요

**학생은 지금처럼 메일을 보내고, 담당자는 정리된 화면에서 확인만 하면 되게 한다.**

1. 담당자 메일로 온 증빙을 서비스가 자동으로 가져온다.
2. Upstage AI가 회의록·영수증에서 값을 읽는다.
3. **코드와 LLM이 지침 항목을 하나씩 판정**하고 근거(원본 위치, 읽은 값, 기준값)를 붙인다.
4. 담당자 화면에 프로그램·팀별로 정리하고 **학생 회신 초안**을 만든다.
5. 담당자가 판정을 확인·수정하고 회신한다.

**핵심 원칙: AI가 결정하지 않는다.** AI는 근거를 정리하고 초안을 만들 뿐, 최종 판단과 회신은 담당자가 한다. 애매하면 `확인필요`로 넘기고, 학생 회신에는 확실한 미충족만 넣는다(허위 지적 방지).

### 1-3. 사용 시나리오

> 월요일 아침, 동아리 담당자가 서비스에 로그인한다. 주말 동안 들어온 12건이 '미확인'으로 쌓여 있다. 정렬을 '해결할 것 먼저'로 바꾸면 부적합·보완필요 건이 위로 온다.
>
> 'AiBara' 건을 연다. 왼쪽에는 회의록 원본, 오른쪽에는 판정 결과가 있다. "회의일(10/30)과 영수증 거래일(10/29)이 다릅니다"를 누르면 원본의 영수증 위치로 이동한다. 확인해 보니 학생이 회의록 날짜를 잘못 썼다. "품목 '와인무화과휘낭시에'에 술 이름 글자가 있습니다"는 확인필요다. 담당자는 디저트임을 확인하고 [충족으로]를 누른다. 종합 판정과 회신 초안이 다시 계산된다.
>
> 회신 초안을 조금 고쳐 학생에게 보내고 [보냈음 표시]를 누른다. 적합인 8건은 근거만 훑어보고 [확인완료]를 누른다.

## 2. 목표와 기대효과

### 2-1. 목표

| 목표 | 측정 |
|---|---|
| 담당자가 메일을 열지 않아도 모든 증빙이 화면에 모인다 | 수집 누락 0건 (팀명 필터·대용량 링크 포함) |
| 지침 항목을 자동으로 판정하고 근거를 보여 준다 | 가상 회의록 72건 회귀 정확도 100%, 실제 제출본 오판 사례별 수정 |
| 허위 지적을 학생에게 보내지 않는다 | 학생 회신에는 미충족만, 확인필요는 담당자 메모 |
| 건당 검토 시간을 줄인다 | 담당자 실사용 전후 건당 처리 시간 비교 (발표 전 측정) |

### 2-2. 기대효과

- **담당자:** 메일함 대신 프로그램·팀별 목록에서 '해결할 것'부터 처리한다. 17개 항목을 눈으로 대조하던 일이 "AI가 표시한 항목만 원본에서 확인"으로 줄어든다. 회신 문장을 처음부터 쓰지 않는다.
- **학생:** 무엇을 고쳐야 하는지 항목별로 명확한 회신을 받는다(예: "참석자 ○○○ 님의 서명이 없습니다").
- **사업단:** 판정마다 기준 버전과 모델이 남아 같은 기준으로 일관되게 검토한다. 지침이 바뀌면 기준만 새 버전으로 확정하면 된다.

## 4. 데이터 구성

### 4-1. 원천 데이터

| 데이터 | 형식 | 출처 | 쓰임 |
|---|---|---|---|
| 회의비 지침 | HWP (별첨1 참고사항) | 사업단 | 판정 기준 추출 |
| 회의록 양식 | HWP (별첨1-1) | 사업단 | 양식 일치 확인(칸 13개) |
| 제출 메일 | MIME (제목·본문·보낸 사람·첨부) | 담당자 학교 메일 → 중계 → 웹훅 | 접수, 팀·프로그램 판별, 제출 기한 |
| 회의록 + 영수증 사진 | HWP 5.0, PDF, 스캔 PDF, DOCX, HWPX, 이미지 | 학생 첨부(10MB 넘으면 네이버 대용량 링크) | 판정 대상 |
| 팀 목록·별칭 | YAML | 사업단 팀 명단 | 팀·프로그램 매칭 |

시범 운영(10/30~11/4): 메일 56건 수집, 그중 관련 없는 메일 19건은 '양식 검토 대기'로 보관, **37건 검수**(동아리 18, 위밋 12, AIM 3, 캡스톤 1, 미확정 3). 첨부 형식은 HWP 23, PDF 18, 스캔 1, 이미지 1.

### 4-2. 수집 방식

담당자 메일은 학교 자체 Exchange(OWA)라 API·외부 전달이 막혀 있었다. 8번의 시도 끝에 다음 경로로 확정했다.

```
학생 → 담당자 OWA (받은 편지함 규칙: 팀 키워드) → 중계 학교 계정(M365)
  → Power Automate (제목·본문·첨부 파일명을 정규화해 팀 키 123개와 비교)
  → submit@jnuai-meetingfee.com → Cloudflare Email Routing → Email Worker → FastAPI 웹훅
```

- 사업단이 **증빙이 아닌 서류가 밖으로 나가는 것**을 꺼려 팀명이 있는 메일만 내보낸다.
- 양식이 아니거나 팀명이 없는 메일은 버리지 않고 '양식 검토 대기'로 보관하고, 개발팀이 주기적으로 확인한 뒤 지운다.

### 4-3. 처리 방식

1. **문서 읽기:** HWP 5.0은 olefile로 표·칸·그림을 직접 읽는다(LibreOffice가 HWP를 읽지 못함). PDF는 pdfplumber, 스캔본은 Upstage OCR.
2. **값 추출:** Upstage Information Extract로 23개 필드(팀명, 회의 일시, 참석자, 가맹점, 주소, 거래일시, 승인번호, 카드번호, 품목, 합계 등)를 뽑는다. **영수증 사진은 원본 해상도로 따로 한 번 더** 읽어 숫자를 맞춘다.
3. **칸 확인:** 서명·영수증은 추출값을 믿지 않고 **칸 안에 그림이 있는지** 문서 리더로 본다. 스캔본은 OCR 좌표로 서명 칸을 찾아 잉크 비율로 판정한다.
4. **판정:** 계산(날짜·시각·금액·지역·기한)은 코드, 의미(주류·장소·회의내용·식비/다과비)는 Solar.
5. **캐시:** 같은 파일은 해시로 캐시해 Upstage에 다시 보내지 않는다(비용·속도·초당 1건 제한).

### 4-4. 판정 기준은 어떻게 만들었나

지침 HWP → Upstage 추출(23개 값) → 코드가 조건 초안 20개 생성 → **담당자 확정** → DB에 버전으로 저장. AI가 만든 조건이 담당자 확인 없이 쓰이지 않는다. 담당자 의견으로 서류로 판정할 수 없는 3개(1일 1회, 수업 시간, 카드 예약)는 제외했고, 운영 중 'R21 영수증 품목 표기'를 추가해 현재 **동아리 기준 v2**(R01~R17, R21)를 쓴다.

## 5. 시스템 구성

### 5-1. 아키텍처

```
[메일] Power Automate → Cloudflare Email Worker → FastAPI /api/intake/mail
[검수] FastAPI 대기열 → LangGraph
        load_files → extract(IE + 영수증 재추출) → read_local | ocr_signature
        → judge_solar → match_team → judge_code → draft
[저장] SQLite (제출·파일·조건 결과·회신·Upstage 캐시·기준 버전)
[화면] React(Vercel) ─ /api ─▶ Cloudflare Tunnel ─▶ FastAPI(Docker, Azure VM)
```

### 5-2. 기술 선택 이유

- **LangGraph:** 형식(디지털/스캔)에 따른 분기와 회의록별 반복을 순서로만 맡기고, 판정 로직은 일반 함수로 둬 시험하기 쉽게 했다.
- **RAG·벡터DB를 핵심 경로에 쓰지 않음:** 추출 필드가 고정이고 기준이 확정 조건이라 검색이 필요 없다. 검색 오차가 판정에 섞이는 것을 피했다.
- **SQLite:** 담당자 2명·팀 100개 규모. `DATABASE_URL`만 바꾸면 Postgres로 옮긴다.

## 6. 검증과 운영 결과

### 6-1. 가상 데이터 회귀

정상·위반 18케이스 × 4형식(HWP·PDF·DOCX·스캔) = **72건, 기대한 조건만 정확히 걸림 72/72.** 스캔본 서명 칸 90/90. 코드를 고칠 때마다 다시 돌린다.

### 6-2. 실제 제출본에서 찾고 고친 것 (시범 운영)

| 사례 | 증상 | 원인 → 수정 |
|---|---|---|
| 영수증이 작게 붙은 PDF | 거래일 10/29를 10/19로, 80,000원을 77,945원으로 읽음 | 문서 전체 추출에서 숫자가 뭉개짐 → 영수증 사진만 원본 해상도로 다시 읽음 |
| 180° 돌린 영수증 | 미리보기가 거꾸로 | HWP 개체 회전각을 읽어 그림을 돌림 |
| 서명 칸이 다음 줄로 떨어진 표 | 학번을 이름으로 읽어 '워드 서명' 오판 | 줄 조각을 한 사람으로 모아 읽음 |
| 카드사 매출전표 가린 번호 | 연구비카드 아님 오판 | 보이는 앞자리로 연구비카드 판별 |
| 36MB 대용량 첨부 | 첨부 0개로 보임 | 네이버 대용량 링크에서 내려받음, 큰 HWP는 사진을 줄인 PDF로 변환해 전송 |
| 한 메일에 회의록 3개 | 첫 파일만 판정 | 회의록마다 판정, 항목 이름에 '[10/27 회의록]' |
| '와인무화과휘낭시에' | 주류로 부적합 | 품목에만 술 글자가 있으면 품목 이름을 적어 확인필요 |

교훈: 판정이 맞아도 **추출값의 형식·해상도, 미리보기 모양**에서 오해가 생긴다. 판정 방식을 바꿀 때마다 실제 제출 전 건을 다시 검수해 판정 변화를 확인했다.

### 6-3. 평가 계획 (발표 전까지)

- 정량: 담당자 실사용 전후 건당 처리 시간, 담당자가 바꾼 판정 비율(판정 수정률), 회신 초안 수정 비율
- 정성: 담당자 인터뷰 인용
